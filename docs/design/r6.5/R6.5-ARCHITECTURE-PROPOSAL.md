## 1. Problem statement

Today, AION milestones already use:

- local directives (`.aion-local/directives/CURRENT.md`)
- Founder authorization script (`scripts/authorize-current-directive.ps1`)
- agent role separation (Grok implement / Claude audit)
- repository baseline gates

What still forces the Owner into routine terminal work is **operational friction**, not missing architecture intent:

1. Authorization is phrase entry in a PowerShell `Read-Host` console.
2. Agents often present commands for the Owner to paste/run when elevation, multi-window, or session limits intervene.
3. Reboot continuation is handoff-file based and easy to mishandle.
4. There is no durable, machine-verifiable **capability envelope** separate from a mutable markdown directive.
5. There is no standing OS-level **operator service** that can run approved work without the chat UI remaining attached.

**R6.5 goal:** after a single Owner approval action for a bounded milestone, Grok/Claude operate PowerShell/npm/node/Docker/Git/tests (and role-permitted edits/commits/pushes) **without asking the Owner to type terminal commands**, while remaining **unable to increase their own authority**.

**R6.5 non-goal:** real authority, private migration, desktop promotion, credential migration, spend systems, or implementing cryptography beyond design.

---

## 2. Design principles

1. **Consent once per milestone, not per command.** Owner approves a bounded envelope; agents execute inside it.
2. **Agents never mint authority.** Only Owner-bound proof transitions pending → authorized.
3. **Directive text is not enough.** A mutable markdown file alone can be edited by a write-capable agent; authority must require a separate Owner proof object.
4. **Least privilege by role.** `GROK_BUILD` ≠ `CLAUDE_AUDITOR` ≠ `OWNER`.
5. **High-consequence still human.** Some operations remain Owner-gated even inside a milestone.
6. **Fail closed.** Missing UI, corrupt store, wrong machine, stale envelope, baseline drift → refuse.
7. **Audit without secrets.** Append-only evidence of approvals and action categories; never recovery passwords, credentials, or private content.
8. **Prepare for R6.6 migration language without performing migration.** Envelopes can later name high-consequence gates without self-approval paths.
9. **No hardware-attestation fiction.** Machine binding is policy + local identity evidence, not TPM quote of agent honesty.
10. **Chat is not the control plane.** ChatGPT Director proposes; Owner UI consents; Operator service executes; agents request/consume envelopes.

## 4. Data objects

### 4.1 Milestone Proposal (Director / agent-authored, non-authoritative)

Human-readable plan: purpose, baseline, roles, risks. Status: `PROPOSED`. Authorizing it does nothing until a Pending Envelope is created and Owner-approved.

### 4.2 Pending Capability Envelope

Machine-oriented request awaiting Owner UI action. Contains all fields in §5. Status: `PENDING_OWNER_APPROVAL`.

### 4.3 Active Capability Envelope

Pending envelope + Owner approval proof + issued timestamps + immutable content hash. Status: `ACTIVE` until completed/expired/revoked/superseded.

### 4.4 Resume Token (reboot-safe)

Narrow continuation object for an already-active envelope after planned reboot. Cannot widen ops; binds to envelope id + machine + baseline + phase cursor.

### 4.5 Execution Receipts

Per action-category records written to append-only log (not full secret-bearing stdout).

### 4.6 Handoff package

Existing AION pattern (LATEST.md + history) remains; R6.5 adds structured envelope finalization record.

## 5. Capability Envelope schema (design)

Logical fields (JSON/CBOR later; design-level names):

| Field | Purpose |
|---|---|
| `envelope_id` | Stable UUID for this approval instance |
| `directive_id` | e.g. `AION-V1.3-R6.5-…` |
| `schema_version` | Envelope format version |
| `title` | Human title |
| `agent_role` | `GROK_BUILD` \| `CLAUDE_AUDITOR` \| future roles |
| `requesting_principal` | Who asked (Director session id / agent session id) — not authority |
| `repository` | Canonical origin URL + local root policy |
| `baseline_head` | Exact Git commit required at start |
| `allowed_head_range` | Optional: only forward ordinary commits from baseline on `main` |
| `authorized_operations` | Typed allowlist (see §6) |
| `prohibited_operations` | Explicit denylist (deny wins) |
| `risk_class` | `ROUTINE` \| `ELEVATED_HOST` \| `HIGH_CONSEQUENCE` |
| `expiration` | Absolute UTC expiry |
| `completion_condition` | e.g. status `AWAITING_CTO_REVIEW` + handoff present |
| `allowed_lifecycle_transitions` | State machine edges permitted under this envelope |
| `commit_push_rules` | branch, no force, no amend, inspect-staged required |
| `host_operation_permissions` | reboot, elevated read-only, BitLocker change, etc. |
| `reboot_continuation_policy` | allowed phases, max reboots, resume token rules |
| `spend_budget` | cents ceiling or `0` / absent |
| `external_action_policy` | none / allowlisted categories |
| `machine_binding` | hostname role, optional SI id when provisioned, policy notes |
| `high_consequence_gates` | list of ops that still require nested Owner approval |
| `owner_approval_proof` | design: signature/HMAC over canonical envelope bytes + approval metadata |
| `approval_timestamp` | set only at Owner approval |
| `content_hash` | hash of all authority-bearing fields excluding proof |
| `supersedes` | prior envelope ids revoked by this approval |
| `not_before` / `not_after` | validity window |

**Deny-wins rule:** if an operation appears in both lists, or is unmarked high-consequence without nested gate, refuse.

## 6. Typed operations catalog

Operations are **named capabilities**, not free-form “run anything.”

### 6.1 Always-mediated runner

Even when `run_powershell` is granted, the Operator Host executes through a policy engine:

- command class allowlist (e.g. `git_status`, `npm_verify`, `docker_ps`, `pwsh_script_in_repo`, `elevated_readonly_probe`)
- working directory jail (repo root, TEMP design dirs, explicit paths)
- env var allowlist
- network mode (default: inherit policy; production AION start still forbidden unless granted)
- timeout + output redaction filters (recovery-password shaped data, tokens)

Free-form arbitrary shell is **not** the default grant. If a milestone needs broader shell, it must be explicit high-risk and still deny credential/authority classes.

## 7. Control-plane services

### 7.1 Approval Ceremony Service

- Accepts Pending Envelope
- Renders Owner UI (see `R6.5-OWNER-UX.md`)
- On AUTHORIZE: verifies machine binding, repo baseline, no conflicting ACTIVE write envelope, then attaches Owner proof
- On DENY: records denial; envelope dead
- Never callable with a “phrase parameter” from agent APIs that bypass UI

### 7.2 Operator Host

Long-lived local process (Owner-started login item or Windows service with tight ACL):

- holds no Owner private keys in agent-accessible memory if avoidable
- verifies Active Envelope before each action class
- enforces role profiles
- issues resume tokens only when reboot policy allows
- single-instance lock for `repo_write_tracked` / commit / push

### 7.3 Agent adapters

Grok/Claude talk to Operator Host via local authenticated channel (named pipe / loopback with OS user ACL), presenting:

- agent role identity (configured by Owner installation, not self-asserted string alone)
- envelope id
- requested operation token + args

Chat agents **do not** receive a raw “become admin” switch.

### 7.4 Director adapter (ChatGPT)

May:

- create proposals
- request pending envelopes
- read audit summaries
- recommend Owner gates

May not:

- approve
- hold Owner approval secrets
- flip lifecycle to AUTHORIZED

## 8. Lifecycle state machine

### 8.1 Envelope lifecycle

```
PROPOSED (optional)
   → PENDING_OWNER_APPROVAL
        → DENIED (terminal)
        → ACTIVE
             → RUNNING_WORK (agent claimed)
             → REBOOT_PENDING (armed)
             → RUNNING_WORK (resume verified)
             → AWAITING_REVIEW (success path)
             → FAILED / BLOCKED (terminal failure)
             → EXPIRED / REVOKED / SUPERSEDED (terminal)
```

### 8.2 Compatibility with existing AION directive statuses

Map, do not abandon:

| Legacy CURRENT Status | Envelope mapping |
|---|---|
| `PENDING_OWNER_AUTHORIZATION` | `PENDING_OWNER_APPROVAL` |
| `AUTHORIZED` | `ACTIVE` (not yet claimed) |
| `RUNNING` | `RUNNING_WORK` |
| `AWAITING_CTO_REVIEW` | `AWAITING_REVIEW` |
| `FAILED` / `BLOCKED` | same |
| `SUPERSEDED` | `SUPERSEDED` |

**Founder-only edge remains:** only Owner approval moves pending → active/authorized. Agents may move `AUTHORIZED→RUNNING` and `RUNNING→{AWAITING_REVIEW,FAILED,BLOCKED}` when envelope allows.

### 8.3 Reboot sub-lifecycle

```
RUNNING_WORK
  → (agent requests planned reboot)
  → policy check + write Resume Token + audit
  → REBOOT_PENDING
  → host restarts
  → Operator Host starts
  → validates Resume Token + envelope still ACTIVE + machine + baseline policy
  → RUNNING_WORK at recorded phase cursor
```

Refusals on resume: wrong machine, envelope expired, baseline unexpected rewrite, token reuse beyond once (if one-time), phase cursor mismatch, host-op not permitted.

## 9. Repository and machine binding

### 9.1 Repository binding

At approval and at every privileged op:

- `git rev-parse --show-toplevel` matches allowed roots
- `origin` URL equals canonical origin
- branch policy (`main` unless envelope says otherwise)
- HEAD is baseline or ordinary-forward descendant per commit rules
- dirty tree rules as envelope specifies (usually clean at start; controlled dirty during work)

### 9.2 Machine binding (honest limits)

Bind to:

- Windows computer name / role label (`DESKTOP TARGET CANDIDATE`)
- optional stable local installation id created at control-plane install (random, stored ACLed)
- later: System Instance id when real SI exists

**Do not claim:** software checks equal hardware attestation or prevent a determined Owner-equivalent local attacker. Threat model is **agent/model overreach and mistaken automation**, not nation-state physical attackers.

### 9.3 Concurrent agents

- Only one `ACTIVE` envelope with `repo_write_tracked` at a time per repository.
- Audit envelopes may run read-only in parallel if they cannot write tracked sources.
- Writer lock file + audit entry; second writer request fails closed.

## 10. Relationship to existing scripts

R6.5 should **wrap and eventually replace UX** of:

- `authorize-current-directive.ps1` (Read-Host phrase)
- manual elevated `Start-Process -Verb RunAs` loops

Migration path:

1. Keep markdown CURRENT as human mirror.
2. Add envelope as authoritative machine artifact.
3. Owner UI calls the same status transition logic as Founder script.
4. Retire phrase-in-shell as primary UX after parity tests pass.
