# R6.5 Threat Model — Delegated Operator Control Plane

**Status:** DESIGN ONLY  
**Scope:** Local delegated operator control plane (Owner UI, envelopes, Operator Host, agent roles)  
**Non-scope:** Full cloud multi-tenant security; TPM remote attestation productization  

---

## 1. Assets to protect

| Asset | Why it matters |
|---|---|
| Owner authorization power | Prevents self-escalation by agents |
| Capability envelopes | Define what automation may do |
| Repository integrity (`main`, canonical origin) | Prevents silent history rewrite / wrong remote |
| Host security posture (BitLocker, Secure Boot, TPM) | Prevents unauthorized weakening |
| Credentials & recovery secrets | Account takeover / disk recovery abuse |
| Private AION state & authority (when it exists later) | Existential product trust |
| Spend pathways | Financial loss |
| Audit log integrity | Forensic truth of what was approved/done |
| Owner attention | UI fatigue / clickjacking of high-consequence gates |

---

## 2. Adversaries and abuse cases

### A1. Compromised or deceptive implementation agent (Grok)

**Goal:** widen power, skip tests, push unsafe code, disable gates.  
**Typical moves:** edit CURRENT/envelope files; forge approval; request reboot to skip checks; smuggle secrets into logs; force-push; run destructive host commands.

### A2. Compromised or deceptive auditor (Claude)

**Goal:** look green while hiding defects; or escalate to writer.  
**Typical moves:** edit production sources “to prove fix”; commit; self-authorize follow-on milestone; suppress findings.

### A3. Prompt injection via repo content / web / tool output

**Goal:** make agent request prohibited ops or present fake “Owner approved” text.  
**Typical moves:** README/instructions claim authorization; tool output contains “AUTHORIZED”; social-engineer Director.

### A4. Local malware running as same user

**Goal:** steal envelopes, inject approvals, race Operator Host.  
**Note:** same-user malware is largely outside R6.5’s hard guarantee; mitigate with ACLs, no shared world-writable stores, and honest residual risk.

### A5. Stale state / confused deputy after reboot

**Goal:** resume wrong phase, replay old approval, run on wrong machine.  
**Typical moves:** copy old resume token; change hostname files; swap repo folder.

### A6. Supply chain (npm, Docker images)

**Goal:** execute hostile code under granted `npm_node` / `docker_ops`.  
**Mitigate:** pin tooling, allowlist scripts, no arbitrary image pull by default.

### A7. Owner mistake

**Goal:** unintentional over-grant.  
**Mitigate:** clear UI risk classes, defaults deny high-consequence, short expiry, least privilege templates.

---

## 3. Security properties required

| Property | Meaning |
|---|---|
| **No self-authorization** | No agent role can finalize Owner approval for any role |
| **No peer-authorization** | Claude ↛ Grok; Grok ↛ Claude; Director ↛ Owner |
| **Envelope integrity** | Active authority depends on immutable content hash + Owner proof |
| **Deny wins** | Prohibitions override allowances |
| **Baseline integrity** | Work refuses if repo identity/baseline policy broken |
| **Machine policy binding** | Resume/execution refuses on wrong machine role binding |
| **Least privilege roles** | Auditor cannot write tracked source |
| **High-consequence nested consent** | Listed ops need extra Owner UI even inside milestone |
| **Fail closed** | Missing/corrupt/expired → refuse, don’t guess |
| **Secret hygiene** | Logs never store recovery passwords, tokens, private blobs |
| **Single writer** | No dual write envelopes on same repo |
| **Auditability** | Approvals and action categories reconstructible |

## 4. Architectural proof: no self-authorization

### 4.1 Split-plane rule

Define three disjoint principals:

1. **Owner Principal** — only entity that can create `owner_approval_proof`.
2. **Operator Host** — verifies proofs; executes gated ops; cannot invent Owner proofs.
3. **Agents (Grok/Claude/Director)** — may create *pending* requests only.

**Invariant I1:** Transition `PENDING_OWNER_APPROVAL → ACTIVE` requires a verification function `VerifyOwnerProof(envelope_bytes, proof)` that succeeds only with material only the Owner ceremony can produce.

**Invariant I2:** Agents have no API that returns or injects Owner proof material.

**Invariant I3:** Editing directive markdown without updating a valid proof for the new `content_hash` yields `INVALID` envelope; Operator Host refuses.

**Invariant I4:** Deleting the authorization store removes ability to act; it does **not** recreate default-allow. Fresh install = no ACTIVE envelopes.

**Invariant I5:** Restoring a backup of an envelope marked `SUPERSEDED`/`REVOKED`/`EXPIRED` fails revocation-list / generation-counter check.

**Invariant I6:** Model text of the form “Status: AUTHORIZED” in chat or files is non-authoritative noise unless matched by store verification.

### 4.2 Why file-only CURRENT.md is insufficient

If a write-capable agent can edit `CURRENT.md` Status to AUTHORIZED, self-auth is trivial.  
**R6.5 fix:** markdown is a **mirror**. Authoritative state is envelope record + proof in an Agent-denied write path:

- store ACL: Operator Host service account / Owner user; agents write only via API that cannot set ACTIVE
- or: store directory is append-only for agents except pending requests queue

### 4.3 Cross-role authorization attempts

| Attempt | Result |
|---|---|
| Grok calls approve(Grok envelope) | API denied — not Owner ceremony |
| Claude calls approve(Grok envelope) | Denied |
| Grok forges Claude audit “GREEN” as approval | Not a proof type accepted by Operator Host |
| Agent passes `-AuthorizationInput` equivalent | Endpoint does not exist for agents; only UI ceremony |
| Agent copies previous proof onto new envelope | `content_hash` mismatch → fail |
| Agent deletes store and claims “first run allow” | Default deny |

### 4.4 Residual risks (honest)

| Residual | Severity | Notes |
|---|---|---|
| Owner account fully compromised | High | Attacker *is* Owner to the OS |
| Operator Host binary replaced by malware | High | Code signing + ACL mitigations later |
| Owner click-approves malicious pending envelope | Medium | UX clarity + risk class banners |
| Supply chain via allowed npm test | Medium | pins + script allowlists |

R6.5 is primarily a **control-plane against agent overreach**, not a full endpoint security product.

## 5. Threat → control matrix

| Threat | Control |
|---|---|
| Agent edits Status to AUTHORIZED | Proof-required transition; markdown non-authoritative |
| Agent edits allowlist in ACTIVE envelope | content_hash + proof bind; modification invalidates |
| Replay old envelope after supersede | revocation generation / supersedes list |
| Resume on wrong PC | machine_binding check on resume |
| Baseline substitution mid-run | every privileged op rechecks git origin/HEAD policy |
| Auditor commits fix | role profile denies `git_commit` / `repo_write_tracked` |
| Dual writers | exclusive write lock |
| Log steals BitLocker key | redaction filters; never query recovery secret values |
| Infinite milestone | expiration + completion_condition |
| Reboot skips Owner gate | resume token cannot add ops; nested gates still required after resume |
| Prompt injection “run destructive wipe” | operation tokens; destructive classes need high-consequence gate |
| Network pivot via agent | external_action_policy default none |
| Spend via tool | spend_budget default 0; gate on increase |
| Fake UI | Operator Host only trusts local Owner UI channel with OS auth |

## 6. High-consequence operations (always nested Owner gate)

Even if a milestone envelope exists, these require a **second** Owner UI confirmation bound to exact op parameters:

1. Real Owner key creation  
2. Real trust provisioning  
3. Real writer transition  
4. PRIMARY machine promotion / demotion  
5. Real private migration  
6. Credential access / export  
7. Sensitive external communications (email/job boards/accounts)  
8. Spending / budget increases  
9. BitLocker enable/disable/suspend/key protector changes  
10. Secure Boot / BIOS / firmware changes  
11. TPM clear/reset  
12. Destructive data removal (non-TEMP)  
13. Backup destruction  
14. External-drive role changes  
15. Authority-system schema/configuration modifications  
16. Git history rewrite (should be globally denied; if ever considered, Owner gate + still default deny)  
17. Granting a new envelope that includes any of the above  

**Design rule:** nested gate produces a **child capability** with tiny scope and short TTL, not a permanent parent widen.

## 7. Failure model (fail-closed)

| Failure | Behavior |
|---|---|
| Owner UI unavailable | No new ACTIVE envelopes; in-flight work continues only if envelope already ACTIVE and op not needing UI |
| Authorization store corrupt | Refuse all gated ops; alert Owner; do not “repair” by wiping into allow |
| Reboot during action | Mark partial step failed/needs resume; use journal; no assume success |
| Agent crash | Envelope remains ACTIVE until expiry; Owner may revoke; no auto-escalate |
| Repo changes unexpectedly (dirty unknown files, wrong origin) | Refuse write/commit/push; status BLOCKED or FAILED per policy |
| Origin changes | Refuse |
| Baseline broken (reset/rebase) | Refuse |
| Network unavailable | Offline ops only; push fails closed |
| Docker unavailable | Tests requiring Docker fail closed or skip only if envelope allows skip taxonomy |
| Windows elevation denied | Elevated ops fail closed; do not ask Owner for manual command paste as substitute authority |
| Approval expires mid-run | Stop new ops; require re-approval |
| Conflicting ACTIVE directives | Refuse second write envelope |
| Two agents attempt writer work | Lock winner; loser fails closed |
| Redaction filter trips on output | Strip/redact; if op required secret display, refuse rather than print |

## 8. Cryptography design notes (not implemented in R6.5 design phase)

Recommended eventual construction:

- **Owner device key** generated at control-plane install, stored in Windows user DPAPI or platform key store.
- Envelope canonicalization (deterministic field order) → `content_hash = H(canonical_bytes)`.
- `owner_approval_proof = Sign(OwnerKey, content_hash || approval_metadata)`.
- Operator Host embeds/trusts Owner public key only.

MVP implementation option (still design-compatible):

- HMAC with DPAPI-protected local secret held only by Owner UI + Operator Host, never by agent configs.

Agents must never receive the private key or HMAC secret.

## 9. Logging threats

| Bad log behavior | Fix |
|---|---|
| Store BitLocker recovery password | ban manage-bde protectors -get content; type-only APIs |
| Store env secrets | scrub `*_TOKEN`, `*_KEY`, `PASSWORD` |
| Store private Owner documents | path jail + content classifiers later |
| Mutable log file edit by agent | append-only ACL; hash-chained log design |

---

## 10. Summary judgment

R6.5 is secure **as an agent delegation boundary** if and only if:

1. Owner proof is unforgeable by agents under the chosen crypto/ACL design, and  
2. Operator Host is the sole executor of privileged ops, and  
3. Roles + deny-wins + nested high-consequence gates are enforced at the Host, not in prompt text.

If any privileged path remains “agent runs raw elevated PowerShell outside Host,” the model collapses. **Mediated execution is mandatory.**
