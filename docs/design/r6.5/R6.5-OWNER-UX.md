# R6.5 Owner UX — Non-PowerShell Authorization Experience

**Status:** DESIGN ONLY  

---

## 1. UX goal

The Owner’s normal loop becomes:

1. ChatGPT (Director) says a milestone is ready.  
2. Owner opens/clicks **local AION Authorization UI**.  
3. Owner reviews a clear card and clicks **AUTHORIZE** or **DENY**.  
4. Grok works autonomously inside the envelope.  
5. Claude audits autonomously (separate envelope or phase).  
6. Owner reads a short review summary (Director and/or UI).  
7. Owner only touches terminals/firmware for **unavoidable** OS/security-secret cases.

The Owner does **not** routinely:

- copy PowerShell blocks from chat  
- manage three service terminals  
- type `npm run verify`  
- type Founder authorization phrases into consoles  
- babysit elevation loops that agents can drive with a single UAC click

---

## 2. Surfaces

### 2.1 Primary: Local Owner Authorization App

**Form factors (pick one MVP):**

| Option | Pros | Cons |
|---|---|---|
| A. Loopback web UI served by Operator Host (`https://127.0.0.1:…` with OS user bind) | Fast to ship; familiar | Must lock to localhost + auth |
| B. Small WinUI/WPF desktop app | Clear OS identity | More UI work |
| C. VS Code/Cursor “AION: Approvals” panel | Dev-centric | Couples to editor |

**Recommendation:** A for R6.5 MVP (localhost only, named-pipe bootstrap token, no LAN bind), with tray icon.

### 2.2 Secondary: High-consequence modal

Same app; full-screen risk styling; requires typing a short confirmation **name of operation** (not a global Founder phrase), e.g. type `ENABLE_BITLOCKER` to confirm — still not PowerShell.

### 2.3 Tertiary: Unavoidable OS UI

BitLocker recovery backup, UEFI/BIOS, UAC Yes/No, printer/USB escrow. These stay native Windows.

### 3.1 Interaction rules

- **AUTHORIZE** disabled until baseline check shows green in UI.  
- **DENY** always available.  
- No default checkbox for high-consequence caps.  
- Showing “ChatGPT says authorize” is informational only; button still required.  
- After authorize: UI shows envelope id + expiry + “Running as GROK_BUILD”.

## 4. End-to-end future conversation shape

### 4.1 Happy path

**ChatGPT:** R6.6 proposal is ready (read-only summary). Pending approval is in your AION Approvals tray.

**Owner:** clicks tray → reviews card → **AUTHORIZE**.

**Grok (via Operator Host):**  
runs verify, implements, commits, pushes if allowed, writes handoffs, sets AWAITING_REVIEW.  
May show progress in chat; does not ask Owner to run commands.

**ChatGPT:** Director review summary (ROUTINE or DIRECTOR REVIEW checkpoint).

**Owner:** clicks **Authorize Claude audit** on a second pending card (or same milestone multi-phase).

**Claude:** audits read-only; writes report; cannot fix source.

**Owner:** reads verdict; decides next milestone.

### 4.2 High-consequence interruption

**Grok:** reaches BitLocker enable step → creates nested gate request → pauses.

**Owner UI modal:**

```
HIGH-CONSEQUENCE GATE
Operation: BitLocker enable on C: (full volume)
Protectors: TPM + RecoveryPassword
Recovery: you must complete Windows escrow UI
[DETAILS] [DENY] [APPROVE THIS OPERATION]
```

**Owner:** approves operation (not “approve anything”).  
**Windows:** BitLocker wizard / UAC as needed.  
**Grok:** resumes only that child capability.

### 4.3 What Owner still might do manually (allowed exceptions)

| Situation | Owner action |
|---|---|
| UAC | Click Yes |
| UEFI Secure Boot | Physical BIOS |
| Recovery key print/USB | Windows UI |
| Approve/Deny milestone | AION UI button |
| Nested high-consequence | AION UI modal |
| Breakglass revoke | AION UI “Revoke all” |

Not required: typing `npm`, `git`, `docker`, Founder phrases, multi-window service babysitting for routine work.

## 5. Checkpoint classes in Owner language

### ROUTINE (no Owner action)

Examples:

- unit/integration tests green, continue next package  
- TEMP fixture cleanup  
- handoff draft updates  
- non-elevated git status  

UI may show live progress; no button.

### DIRECTOR REVIEW (ChatGPT reads; Owner no shell)

Examples:

- milestone complete summary  
- medium findings triage  
- whether to request Claude audit  

Owner may just read chat. Optional “Ack” in UI without new powers.

### OWNER GATE (explicit button)

Examples:

- authorize milestone envelope  
- nested BitLocker/Secure Boot  
- real migration / writer cutover (future)  
- spend / credentials  
- revoke agent rights  

---

## 6. Notifications

- Tray: pending approvals count  
- Optional Windows toast for OWNER GATE only (not every test)  
- Never toast secrets  

---

## 7. Accessibility & safety UX

- Color is not the only risk signal; include text risk class.  
- AUTHORIZE requires deliberate click; no Enter-to-approve on page load.  
- For HIGH CONSEQUENCE parent envelopes, require 2-step: review → confirm.  
- Show **diff of permissions vs last envelope** when superseding.  
- Always show **Forbidden** list even if long.  

---

## 8. Failure UX

| Condition | Owner sees |
|---|---|
| Baseline mismatch | AUTHORIZE disabled + “Repo HEAD ≠ baseline” |
| Wrong machine | Banner refuse |
| UI cannot reach Operator Host | “Control plane unavailable — agents cannot gain new authority” |
| Envelope expired | “Expired — request new approval” |
| Agent needs elevation | Single UAC prompt from Host, not a chat script dump |

---

## 9. Anti-patterns to reject

1. “Paste this into PowerShell to authorize.”  
2. Agent says “I’ve authorized myself pending your silence.”  
3. Chat-only approval without local UI/proof.  
4. Global “Allow all shell forever” toggle.  
5. Hiding nested gates inside routine authorize.  

---

## 10. MVP click path (R6.5 implementation target)

1. Install/start Operator Host (once per machine).  
2. Open Approvals UI.  
3. See pending milestone.  
4. Click AUTHORIZE.  
5. Watch status RUNNING without typing shell.  
6. On completion, see AWAITING_REVIEW + open handoff link.  

That is the definition of UX success for R6.5.
