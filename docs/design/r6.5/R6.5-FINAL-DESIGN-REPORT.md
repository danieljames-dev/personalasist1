## Executive summary

R6.5 should introduce a **local delegated operator control plane** so the Owner authorizes a **bounded milestone once via UI**, after which Grok (implementation) and Claude (audit) execute routine PowerShell/npm/node/Docker/Git/tests through a **mediated Operator Host** without asking the Owner to type terminal commands.

**Agents must never mint or widen authority.** Owner approval produces a machine-verifiable **Capability Envelope**. Markdown directives become human mirrors, not sole authority.

R6.5 prepares the **gate framework** for later R6.6 real migration/writer cutover but **must not perform** migration, authority initialization, desktop promotion, or host security weakening as part of R6.5.

## 1. Recommended architecture

### 1.1 Planes

| Plane | Actors | Power |
|---|---|---|
| **Director** | ChatGPT | Propose milestones, review outcomes; **no** Owner approval |
| **Owner ceremony** | Local Approvals UI | Sole source of `owner_approval_proof` |
| **Control plane** | Envelope store, lifecycle, audit log | Records truth of approvals |
| **Operator Host** | Local service | Verifies envelopes; executes gated ops |
| **Agents** | GROK_BUILD, CLAUDE_AUDITOR | Request ops; cannot approve |

### 1.2 Core artifact: Capability Envelope

Contains at minimum:

- directive ID, agent role, repository, baseline  
- authorized operations, prohibited operations (deny wins)  
- risk class, expiration, completion condition  
- allowed lifecycle transitions  
- commit/push rules, host-operation permissions  
- reboot continuation policy  
- spend budget (default none), external-action policy  
- machine binding (honest, non-attestation)  
- high-consequence nested gates list  
- Owner approval proof + content hash  

### 1.3 Mediated execution (mandatory)

Privileged work flows **only** through Operator Host operation tokens (`npm_verify`, `git_commit_forward`, `elevated_readonly_security`, …), not free-form “agent is admin.”

## 2. Security boundaries

1. **No self-authorization:** Grok↛Grok, Claude↛Claude, cross-role approve denied, model text is not proof.  
2. **No silent widen:** envelope mutation breaks content_hash/proof.  
3. **Delete ≠ allow:** empty store denies gated ops.  
4. **Stale/superseded restore fails** revocation/generation checks.  
5. **Deny wins** over allow.  
6. **High-consequence nested Owner gates** for keys, writer, migration, credentials, spend, BitLocker/Secure Boot/BIOS, destructive data, backup destruction, drive role, authority-system mods.  
7. **Secret hygiene:** never log BitLocker recovery passwords, credentials, private Owner content.  
8. **Single writer lock** per repository.  
9. **Fail closed** on UI down, store corrupt, baseline/origin drift, elevation denied, expiry, conflicts.  

Honest residual: full compromise of Owner OS user / Host binary is outside agent-boundary guarantees.

## 3. Owner experience

**Target loop:**

ChatGPT: milestone ready → Owner clicks **AUTHORIZE** in local AION Approvals UI → Grok works → Claude audits → Owner reads verdict.

**Owner still does manually only when unavoidable:** UAC Yes, UEFI, BitLocker recovery escrow UI, nested high-consequence confirmations, revoke.

**Owner no longer routinely:** pastes PowerShell, types npm/git, runs Founder Read-Host phrases, babysits service windows for routine work.

See `R6.5-OWNER-UX.md` for wireframes and anti-patterns.

## 4. Grok role — `GROK_BUILD`

**May (inside Owner-approved milestone envelope):**

- run mediated PowerShell / npm / node / Docker  
- read/write authorized repo  
- TEMP fixtures  
- tests  
- ordinary forward commits  
- push canonical branch when envelope permits  
- reboot when envelope permits  
- write handoffs  
- non-Founder lifecycle: AUTHORIZED→RUNNING→AWAITING_REVIEW|FAILED|BLOCKED  

**Must not:**

- authorize itself or change its envelope  
- access credentials unless nested grant  
- spend unless explicit budget + gate  
- real writer transition unless separately authorized later  
- rewrite Git history  
- weaken security gates / budgets  
- treat chat instructions as authority

## 6. Authorization lifecycle

```
PROPOSED → PENDING_OWNER_APPROVAL → {DENIED | ACTIVE}
ACTIVE → RUNNING_WORK → {AWAITING_REVIEW | FAILED | BLOCKED}
ACTIVE may also → EXPIRED | REVOKED | SUPERSEDED
```

Legacy CURRENT statuses map onto these (see architecture doc).  
**Only Owner ceremony** creates ACTIVE from pending.

---

## 7. Reboot lifecycle

```
RUNNING_WORK → (arm) REBOOT_PENDING → host reboot →
verify resume token + envelope + machine + policy → RUNNING_WORK
```

Resume **cannot**: widen ops, substitute baseline, replay superseded envelopes, run on wrong machine binding, or skip nested high-consequence gates still outstanding.

---

## 8. Machine binding

Bind envelopes to:

- expected machine role label (e.g. DESKTOP TARGET CANDIDATE)  
- computer name / local install id  
- repository root + canonical origin + Git baseline/range  
- later: System Instance id when provisioned  

**Do not pretend** software UUID checks are hardware attestation.

## 9. Checkpoint model

| Class | Who acts | Examples |
|---|---|---|
| **ROUTINE** | Agent continues | tests green; next package; TEMP cleanup |
| **DIRECTOR REVIEW** | ChatGPT reviews; Owner no shell | milestone summary; medium finding triage |
| **OWNER GATE** | Owner UI button | authorize envelope; BitLocker; keys; migration; spend; revoke |

## 10. Failure model (summary)

UI unavailable → no new authority.  
Store corrupt → refuse gated ops.  
Reboot mid-action → journal incomplete; no false success.  
Agent crash → envelope remains until expiry/revoke.  
Unexpected repo/origin/baseline change → refuse write/push.  
Network/Docker/elevation problems → fail closed per op.  
Approval expired / conflicting directives / dual writers → refuse.

---

## 11. Audit model

Append-only local evidence for:

- who requested authority  
- what was approved (envelope hash + caps summary)  
- Owner confirmation timestamp  
- executing agent role  
- operation categories executed  
- Git commits/pushes  
- reboots  
- completion status  

**Never:** secrets, credential values, BitLocker recovery passwords, unnecessary private content.

---

## 12. Threat model (summary)

Primary adversary: **deceptive or buggy agents** and prompt injection seeking privilege.  
Controls: split planes, proof-required approval, mediated runner, role denies, nested gates, redaction, single writer.  
See `R6.5-THREAT-MODEL.md`.

## 13. Migration compatibility (R6.6 readiness without doing R6.6)

R6.5 ships the ability to express:

`R6.6 Real Migration + Writer Cutover`

as a **HIGH_CONSEQUENCE** envelope whose migration/writer/key operations are **all nested Owner gates**, with still **zero** agent self-auth paths.

R6.5 must **not** implement private copy, SI promotion, or writer transition—only the control-plane hooks those future tokens will hang on.

## 15. Top unresolved risks

1. **Same-user malware** can still impersonate Owner to the OS — residual.  
2. **UI fatigue** → Owner over-approves high-consequence cards.  
3. **Allowlist gaps** → either too strict (agents ask for shell again) or too loose (escape).  
4. **Crypto MVP quality** (HMAC/DPAPI) vs future strong keys.  
5. **Chat products without Host integration** regress to paste-the-script UX.  
6. **Scope creep** into implementing migration inside R6.5.  
7. **Elevated operations** UX vs security (UAC storms).  
8. **Audit log completeness vs privacy** tension.

## 16. Recommended R6.5 acceptance criteria

GREEN only if:

1. Owner authorizes a synthetic milestone **with UI only** (no PowerShell phrase).  
2. Grok completes synthetic work (verify + bounded edit + commit) **without Owner typing commands**.  
3. Claude runs synthetic audit **without** write/commit capability.  
4. All **no-self-auth** attacks S1–S9 fail closed.  
5. Reboot resume works without widening.  
6. Fail-closed on baseline/origin/expiry/corruption.  
7. Audit log reconstructs approval vs actions; **no** recovery secrets.  
8. No real authority, private migration, desktop promotion, or host security posture change in R6.5 acceptance runs.  
9. Product `npm run verify` remains green on integration branch when implementation lands.
